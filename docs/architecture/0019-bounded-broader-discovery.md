# Decision 0019 — Reviewed bounded broader discovery

Date: 2026-10-05. Status: implemented for local development; interactive/native/live-provider release checks pending.

## Problem and plan

A single ten-result response cannot exercise a 30–50-opportunity shortlist. Offer broader discovery without unconstrained generated queries or unlimited provider spending. The engine builds five exact variations from the same controlled reviewed categories, replacing only the fixed intent token: jobs, job openings, vacancies, hiring, careers. Role, region, arrangement, seniority and selected skill terms are retained in every query. The plan itself is shown before dispatch and exactly rebuilt/revalidated at the authenticated search boundary and for every adapter request. Queries never come from resume text, result content or a model.

The plan has version 1, at most five sequential basic Tavily requests, ten candidates per response, at most 50 raw candidates, a 75-second total wait budget and an estimated five-credit ceiling. No automatic retry or continuation. Users can opt out for the existing single basic request. Pricing is guidance rather than measured billing: [Tavily basic search pricing](https://help.tavily.com/articles/6938147944-basic-vs-advanced-search-what-s-the-difference) states one credit per basic search; reviewed 2026-10-05. [Official parameter guidance](https://github.com/tavily-ai/skills/blob/main/skills/tavily-best-practices/references/search.md) documents explicit search depth and auto-parameter risks. Keep depth basic and auto_parameters false; provider billing governs actual charges, including uncertain failed/cancelled requests.

## Lifecycle and replaceable boundaries

The existing single-search route and provider contract remain; the provider gains a restricted search_variant method. A small in-process broader-discovery coordinator owns sequential dispatch, deadline, transient counts and cancellation. One application search lock covers both single and broader dispatch. A session-local UUID identifies a run; a bounded 32-entry cancellation/replay memory prevents late cancellation races and immediate replay. No durable run, query, profile or candidate record is added. One progress record is retained until the next broader run; IDs are never sent to Tavily.

The plan preview uses `/api/v1/search/plan`; submission adds exact reviewed_plan and run_id to the existing confirmation. Fixed authenticated progress/cancel routes operate only on UUIDs. Browser and Tauri bridges expose these specific local routes. Browser polling is bounded to the active wait with no overlapping polls. The native main wait allows 85 seconds so the engine deadline can return partial results. Single-search response validation remains ten-result; broader response/analysis validation permits 50 with coverage accounting. Local assistance input remains bounded at 3 MB, and analysis stays on the existing worker-thread path. Restart/rebuild engine and frontend together for the new commands/contracts; no storage migration.

Stop discovery sends an explicit local cancellation request, cancels the active adapter wait and skips future requests, returning completed results. Changing search context or disconnecting asks for cancellation and discards stale UI responses. A cancellation request can fail if local connectivity is lost; the UI says confirmation is pending and the 75-second engine limit still applies. A sent provider request cannot be recalled and may cost credits. This differs from single-search Stop waiting, which discards the reply.

Provider failure (including malformed/unsafe results, quota, authentication and rate limiting) stops the plan immediately, with fixed failure metadata and earlier safe results preserved. Timeout and cancellation also preserve earlier results. No blind retries. Results disclose attempted/completed counts and stop reason, even if empty. Canonical links are deduplicated across responses; first occurrence and provider/plan order survive ties. Unknown content stays reviewable and local filters/classification remain separate. The app never fetches result pages or embedded resources.

## Evidence, limitations and setup

Synthetic tests cover all five captured public requests, 50 unique candidates, cross-response tracking variants, stale/altered/private plan rejection before key reads, active/pre-dispatch cancellation, lock recovery, overall deadline, replay, later unsafe results and partial failures. Frontend checks cover full disclosure, limits, progress, partial retention, safe fixed control routes and response-mode mismatch.

Five intent variations may heavily overlap and careers queries can return navigation/resources. Fifty candidates is a ceiling before deduplication/filtering, not 50 verified suitable jobs. The independent diagnostic corpus now includes one deliberately constructed 50-candidate pool; it demonstrates scale/retention but is not a representative quality estimate. Broader discovery does not fix wrong-role ordering, negation, cloud aliases, freshness or eligibility. Live-provider coverage/cost/resource evaluation and interactive browser/native cancellation/accessibility/theme checks are still required before milestone 17 or alpha readiness can be claimed.

No additional provider, key, permission, model or dependency is needed. Existing setup/skip paths remain. Preview states request count, expected credit ceiling, endpoint, data disclosure and optional single-search recovery. Provider errors guide users to key replacement, quota dashboard or later explicit retry. Revisit pricing/discovery breadth after deliberate reviewed live evaluation; no background/recurring search is introduced.
