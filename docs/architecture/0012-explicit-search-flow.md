# Explicit first search flow

Discover now connects the bounded adapter in decision 0011 to a separate explicit Send action. Preparing a preview remains local; saved Tavily configuration reports dispatch availability, not accepted authentication or guaranteed credits. Review enables Send. Each Send consumes the UI review, so another request or retry requires another deliberate review. No search starts on launch, navigation, criteria edits, key setup or connection checking.

The authenticated POST /api/v1/search accepts exactly criteria, provider=tavily, query_version=1, reviewed_query and confirmed=true. JSON is bounded at 6144 bytes and five seconds; duplicate/unknown fields, wrong types/version/provider and stale or private query/criteria are rejected before key access. The engine rebuilds the controlled query and compares it with the displayed query, then reads the vault key under its lock. One engine-wide search lock rejects concurrent dispatch; failures release it. The adapter revalidates criteria and review again immediately before its fixed request. API responses are no-store, contain only query/provider/candidates or fixed recovery codes, and never return credentials. Confirmation is per HTTP request, not a durable permission or background policy.

The browser bridge uses one fixed local route, the existing custom-header development guard, omitted browser credentials, no-store, redirect rejection and a thirty-second wait. The native job_search command uses the authenticated fixed local route, a bounded JSON body and thirty-second wait; it has no provider endpoint or key argument. Provider traffic stays in the engine. Native and browser generations discard late responses after Stop waiting, edits, Settings navigation, disconnect or unmount. Stop waiting does not promise to recall a sent request; bounded engine work may finish and consume credits. Immediate retry may receive search_busy. There are no automatic retries.

App-level search state survives ordinary page navigation. Criteria edits or opening Settings synchronously discard result/error/pending state and preview/review. Every successful response must match the exact query, provider and bounded candidate schema. The UI presents title, URL and snippet as React text nodes; HTML/instructions remain escaped text. No anchor, image, iframe, remote resource, automatic link open or detail scraping is introduced. URLs are selectable for manual use; explicit validated external opening is a later increment. Results are session-only and clear on reload/exit or Clear results. They are web search candidates rather than verified vacancies, ranked matches or guaranteed preference filters; no freshness claim is made.

Evidence: 232 engine tests and 32 frontend tests pass. API captures use a distinctive synthetic private profile, assert no profile access, compare the outgoing query with its preview, and cover auth, confirmation, private/extra fields, malformed/bounded JSON, vault failures, fixed provider errors and overlap/recovery. Frontend tests cover request routing/body/options, review gating/consumption, duplicate sends, late-response invalidation, retries, schema/query mismatch and actual React rendering of malicious markup without executable tags or resource attributes. Frontend typecheck/build and Windows Rust/NSIS packaging pass. Browser automation could not start (kernel exited), so visual/keyboard/theme/window and native interaction remain unverified. No real key or live Tavily call was used. Public-release claims still require interaction checks and deliberate live-provider verification.
