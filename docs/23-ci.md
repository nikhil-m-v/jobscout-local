## Checks and artifacts

[Windows CI](../.github/workflows/windows-ci.yml) runs on pull requests, pushes to `main`, and manual dispatch. It uses GitHub-hosted `windows-2025` x64 runners, Node 24, Python 3.12 and Rust 1.98.1 MSVC for packaging. All external actions are pinned to full commit hashes. The token has only `contents: read`, checkout does not retain credentials, and there is no signing, release publication, privileged pull-request trigger or self-hosted runner.

There is no repository-privacy check or visibility prerequisite. The same validation and packaging jobs can run in public and private repositories. Repository settings remain the owner's responsibility.

The **Synthetic validation (Windows)** check runs directly on each workflow trigger:

1. The complete engine suite, including Windows path and isolated synthetic Credential Manager integration tests.
2. All frontend regressions, offline report/audit tests and synthetic dependency-notice checks.
3. Synthetic shortlist and candidate-pool evaluations, plus verification of checked-in public query plans without dispatch.
4. Frontend typechecking and the production frontend build.

The same runner is available locally after the development setup in [README](../README.md):

```powershell
npm.cmd run validate:ci
```

Each invocation creates a new ignored `work/ci/validation-*` directory. It writes per-check logs, engine JUnit XML and a JSON pass/fail summary. All nine steps run even if an earlier check fails; any nonzero exit, process-start failure or five-minute step timeout makes the command fail. Reports are not evidence that every check passed: inspect the summary and GitHub check result. The workflow additionally has bounded job timeouts and cancels superseded runs on the same branch or pull request.

**Windows installer** depends on successful validation. A fresh job installs the packaging dependencies and runs `npm.cmd run package:installer`, building the paired frozen engine, frontend, native shell and NSIS installer into `work/ci-target`. The wrapper checks restricted bundle configuration, rejects source maps/raw development files in the built frontend, requires exactly one current-version installer and stages only that executable in a fresh `work/distribution/build-*/installer` folder. The workflow also checks that npm/Cargo lockfiles remain unchanged. A separate package audit binds the staged installer's filename, byte count and SHA-256 to the checked-out revision and workflow run. For pull requests that revision is the tested merge commit.

The three artifact names start with `synthetic-reports-`, `unsigned-windows-x64-` and `package-audit-`, followed by the revision and attempt. Retention is seven days. Reports, the unsigned installer and the package audit have the repository's current artifact access settings; treat them as publicly accessible during public development. Report uploads allow only top-level generated logs/XML/summary files; pytest databases, temporary documents and other workspace content are excluded. The package upload names only the staged installer and happens only after success; the audit is uploaded separately. Uploads contain only the allowlisted synthetic reports, staged installer and package audit; local career data, credentials and debugging workspaces remain excluded. These are CI build artifacts, not an approved major-release download. The unsigned installer is a test build; no installation or interactive acceptance happens in this workflow.

After packaging, the job also runs the [23D frozen-sidecar lifecycle check](23-lifecycle.md). It verifies actual frozen parsing, cancellation of an incomplete import upload on normal/forced owner exit, listener closure, saved-profile restart and database integrity in newly created synthetic storage. The report includes the tested engine hash, fixed outcome fields and timings, with no workspace paths, tokens or career records. Its exact report path is retained with the packaging audit, including on a lifecycle failure after packaging succeeds; a failed check prevents the normal installer upload. This check passes locally and in the main-push run above. The later [23E extension](23-installed-lifecycle.md) additionally requires real workspace health, with its existing optional local-runtime status probe on loopback; this extension has local frozen/installed evidence only.

## Privacy and dependencies

[Milestone 23C](23-dependency-notices.md) collects dependency notices before production packaging and includes one exact text resource in the installer. Missing package texts, unmapped frozen Python inputs or changed override checksums stop packaging. The package audit includes the inventory and notice hash. Legal/source-availability review remains open; a successful collection does not approve public release.

Routine checks use checked-in synthetic inputs and mocked provider transports. There is no provider secret, account connection check, live search, result-page fetch, private profile, model download or inference in the workflow. The Windows credential integration test creates and removes its own synthetic entries under unique temporary workspace identities; it does not use real provider keys.

Dependency setup and build-tool acquisition use the network for npm, Python packages, Rust/Tauri tools and GitHub Actions. These build requests are distinct from application discovery. No application provider permission is granted by CI. Downloaded tool/package versions and upstream availability can change: npm and Cargo have checked-in lockfiles, but Python dependencies retain the project's existing version ranges; Node/Python patch versions and the hosted image also float. This slice does not claim bit-for-bit reproducible packages. Dependency locking and signing need separate release work.

Keep local reports ignored. Uploads in the workflow come from disposable hosted workspaces, not a maintainer's existing `.local`, `work` or career-data folders. Review changes to workflow/scripts/fixtures before trusting an artifact, including artifacts built from contributor branches.
