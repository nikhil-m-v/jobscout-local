## Checks and artifacts

[Windows CI](../.github/workflows/windows-ci.yml) runs on pull requests, pushes to `main`, and manual dispatch. It uses GitHub-hosted `windows-2025` x64 runners, Node 24, Python 3.12 and Rust 1.98.1 MSVC for packaging. All external actions are pinned to full commit hashes. The token has only `contents: read`, checkout does not retain credentials, and there is no signing, release publication, privileged pull-request trigger or self-hosted runner.

The **Private source policy** check requires the event's repository privacy flag to be exactly true; false or missing metadata fails before source checkout. This does not hide existing public source or change repository settings.

The dependent **Synthetic validation (Windows)** check runs:

1. The complete engine suite, including Windows path and isolated synthetic Credential Manager integration tests.
2. All frontend regressions, offline report/audit tests and synthetic dependency-notice checks.
3. Synthetic shortlist and candidate-pool evaluations, plus verification of checked-in public query plans without dispatch.
4. Frontend typechecking and the production frontend build.

The same runner is available locally after the development setup in [README](../README.md):

```powershell
npm.cmd run validate:ci
```

Each invocation creates a new ignored `work/ci/validation-*` directory. It writes per-check logs, engine JUnit XML and a JSON pass/fail summary. All nine steps run even if an earlier check fails; any nonzero exit, process-start failure or five-minute step timeout makes the command fail. Reports are not evidence that every check passed: inspect the summary and GitHub check result. The workflow additionally has bounded job timeouts and cancels superseded runs on the same branch or pull request.

**Windows installer** depends on successful validation. A fresh job installs the packaging dependencies and runs `npm.cmd run package:installer`, building the paired frozen engine, frontend, native shell and NSIS installer into `work/ci-target`. The wrapper checks restricted bundle configuration, rejects source maps/raw development files in the built frontend, requires exactly one current-version installer and stages only that executable in a fresh `work/distribution/build-*/installer` folder. The workflow also checks that npm/Cargo lockfiles remain unchanged. A separate private audit binds the staged installer's filename, byte count and SHA-256 to the checked-out revision and workflow run. For pull requests that revision is the tested merge commit.

The three artifact names start with `synthetic-reports-`, `unsigned-windows-x64-` and `private-package-audit-`, followed by the revision and attempt. Retention is seven days, within the private source repository. Report uploads allow only top-level generated logs/XML/summary files; pytest databases, temporary documents and other workspace content are excluded. The package upload names only the staged installer and happens only after success; the audit is uploaded separately. No report, audit, source archive or source repository is a public download. The unsigned installer is a test build; no installation or interactive acceptance happens in this workflow.

## Privacy and dependencies

[Milestone 23C](23-dependency-notices.md) collects dependency notices before production packaging and includes one exact text resource in the installer. Missing package texts, unmapped frozen Python inputs or changed override checksums stop packaging. The private audit includes the inventory and notice hash. Legal/source-availability review remains open; a successful collection does not approve public release.

Routine checks use checked-in synthetic inputs and mocked provider transports. There is no provider secret, account connection check, live search, result-page fetch, private profile, model download or inference in the workflow. The Windows credential integration test creates and removes its own synthetic entries under unique temporary workspace identities; it does not use real provider keys.

Dependency setup and build-tool acquisition use the network for npm, Python packages, Rust/Tauri tools and GitHub Actions. These build requests are distinct from application discovery. No application provider permission is granted by CI. Downloaded tool/package versions and upstream availability can change: npm and Cargo have checked-in lockfiles, but Python dependencies retain the project's existing version ranges; Node/Python patch versions and the hosted image also float. This slice does not claim bit-for-bit reproducible packages. Dependency locking and signing need separate release work.

Keep local reports ignored. Uploads in the workflow come from disposable hosted workspaces, not a maintainer's existing `.local`, `work` or career-data folders. Review changes to workflow/scripts/fixtures before trusting an artifact, including artifacts built from contributor branches.

Record the run URLs, revision and actual counts rather than assuming local evidence proves hosted success. Private-repository Actions quotas and protection features depend on the account plan; no plan upgrade or paid execution is authorized here.

Then configure the main-branch protection/ruleset to require **all three** `Private source policy`, `Synthetic validation (Windows)` and `Windows installer`, with their observed GitHub Actions check identities. Requiring upstream checks separately prevents a skipped dependent job from standing in for passed tests. Enforced settings are not created by this YAML; repository permissions/settings remain GitHub concerns.
